## 2. Answers I can now give

### On "APK budget" — plain answer

An APK/AAB budget is just **a number you decide in advance for how big the app download is allowed to be**, so that size decisions get made deliberately instead of by accumulation.

It matters for three practical reasons:

1. **Install conversion.** Play Store install rates drop measurably as size grows, most sharply on cheaper devices and metered connections — which is a large share of Android.
2. **Google Play's instant-uninstall pressure.** Big apps are what people delete first when storage runs low.
3. **It forces a ranking.** Without a number, "bundle all 12 fonts" and "add paper grain" both sound free. With a number, they compete.

For Notesup concretely:

| Item | Cost |
|---|---|
| Compose + Material3 + Room + Hilt + Coil baseline | ~4–5 MB |
| Jetpack Ink (native `.so` per ABI) | ~2–3 MB |
| Roboto Flex variable | ~1.6 MB |
| Each extra bundled font family | ~0.4–0.9 MB |
| ~60 vector icons | ~40 KB (negligible) |
| Paper grain tile PNG | ~10 KB (negligible) |
| Baseline profile | ~100 KB |

**My recommendation: set the budget at 15 MB download.** That comfortably fits Grok's "bundle 4 + on-demand 8" plan with room for ink and grain, and it's small enough to feel light. Note that AAB + per-ABI splits means the *download* is roughly half the universal APK, so measure the number Play actually reports, not the file on disk.

**Practical rule:** anything over 500 KB gets an explicit line in `BUILD.md`. Everything under is free.

## 3. 🔴 A "law" in the spec is not achievable as written

### F-25 — You cannot have "no splash." Android 12+ enforces one.

`BUILD.md:1251` bans "splash logo." `ui/05-MOTION.md:26` says *"Cold start: None. First frame is home."*

**From Android 12, the system splash screen is shown at every cold start. It is not opt-out.** You only control what it looks like and when it dismisses. So the law as written is unimplementable, and worse, ignoring it means you get the *default* — your launcher icon on a `windowBackground` colour you never chose, which on a paper-coloured app will very likely flash the wrong colour.

**Solution — turn a banned thing into a designed 400 ms.** This is one of the few moments every single user sees every single cold start.

```xml
<style name="Theme.Notesup.Starting" parent="Theme.SplashScreen">
    <item name="windowSplashScreenBackground">@color/paper</item>          <!-- #F6F1EA -->
    <item name="windowSplashScreenAnimatedIcon">@drawable/ic_launcher_foreground</item>
    <item name="postSplashScreenTheme">@style/Theme.Notesup</item>
</style>
```
```kotlin
// MainActivity.onCreate, BEFORE super.onCreate()
val splash = installSplashScreen()
splash.setKeepOnScreenCondition { !viewModel.roomReady }   // ~0 ms in practice
```
Rules that keep it inside your aesthetic:
- Background is **`paper`**, so the splash *is* the page. The transition to home becomes "the page was already there" instead of a colour flash.
- **No wordmark, no tagline, no animation of your own.** The wax seal on cream, system-sized. It's the launcher icon, nothing added.
- Dismiss the instant Room has rows. Do **not** hold it for a minimum duration — that's the thing you were right to ban.
- Add `androidx.core:core-splashscreen` for consistent behaviour back to API 23.

Then rewrite the law honestly: **"No custom splash. The system splash is paper-coloured and dismissed on first Room emission."** Same intent, achievable.

> **DECISION F-25:** ⬜ open — adopt the designed system splash?

## 4. Component swaps worth making

### F-26 🟢 `ListDetailPaneScaffold` instead of a hand-rolled two-pane

`BUILD.md:599` specifies tablet as "list 360 dp | editor fill, shared element disabled, crossfade 160 ms." That's re-implementing a Material canonical layout by hand, and worse than the real one.

**Use `androidx.compose.material3.adaptive:adaptive-layout`'s `ListDetailPaneScaffold`.** It's the Material-opinionated list-detail canonical layout, adapts automatically across window size classes, and — the part that's genuinely premium — recent versions support **`PaneExpansionState`**: the user can *drag the divider* to change the pane split, and you can set it at runtime.

For a notes app, drag-to-resize the list/editor split is exactly the kind of thing a tablet user notices and a phone-port doesn't have. You also get correct back behaviour between panes for free, which the hand-rolled version would have to solve.

```kotlin
implementation("androidx.compose.material3.adaptive:adaptive-layout:<current>")
implementation("androidx.compose.material3.adaptive:adaptive-navigation:<current>")
```
Keeps §9's rail. Replaces only the two-pane hand-roll.

> **DECISION F-26:** ⬜ open

### F-27 🟢 `androidx.graphics:graphics-shapes` — real shape morphing, and squircle cards

This is the official AndroidX library behind M3 Expressive's shape system: `RoundedPolygon` for shapes, `Morph(start, end)` for animating between them with a 0→1 progress.

Two uses, both high value:

**(a) The checkbox morph (F-20.2).** You need a shape that animates as it fills. `Morph` is precisely that, and hand-rolling it with `RoundedCornerShape` interpolation looks wrong at the midpoint.
```kotlin
val ring = RoundedPolygon.circle(radius = 11f)
val filled = RoundedPolygon(numVertices = 8, radius = 11f, rounding = CornerRounding(0.85f))
val morph = remember { Morph(ring, filled) }
// drive progress with the same spring the fill uses
```

**(b) Squircle note cards — the one I'd actually push for.** Right now cards are `RoundedCornerShape(24.dp)`, which is a circular-arc corner. Continuous-curvature corners (squircles) are a large part of why iOS surfaces read as expensive, and M3 Expressive's expanded shape library is Google's answer to exactly that. `RoundedPolygon` with high `rounding.smoothing` gives you continuous curvature natively.

This is a **one-line change to your card shape** that alters the perceived quality of every screen, because the card is the repeated object. It also directly serves `ui/00-ANTI-JOKE.md`'s grayscale test — a squircle grid reads as designed in grayscale where a rounded-rect grid reads as Material default.

Caveat, stated honestly: converting `RoundedPolygon` → Compose `Shape` goes through `Path`, so measure it in the grid before committing. If it costs frames at 4 columns, it goes back to `RoundedCornerShape` and nothing else changes.

> **DECISION F-27:** ⬜ open — (a) checkbox morph, (b) squircle cards, or both?

### F-28 🟡 The pin strip wants to be a Carousel — but I'd hold

`ui/06-HOME.md:42-48` specs the pin strip as a `LazyRow` of 148×152 cards. Material3 has `HorizontalMultiBrowseCarousel`, which lays items out at large/medium/small sizes and masks them so they smoothly expand and collapse as you scroll. It's the Expressive component built for "quick browse of small content."

It would look expensive immediately. **But I'd hold**, for a reason consistent with your own laws: the carousel *changes item size by scroll position*, which means your pinned notes render at three different sizes depending on where they've been scrolled to. Pins are supposed to be equals — `ui/06-HOME.md:48` says "the strip *is* the heading." A component that visually ranks them contradicts that.

Recording it because it's the right instinct on the wrong element. If you ever build a "recently viewed" or media strip, that's where the carousel belongs.

> **DECISION F-28:** ⬜ open — I lean hold. Overrule if you want it.

## 5. Libraries — verified, and what each one buys

Every coordinate below was checked this session.

### F-29 🟢 Telephoto for the image lightbox — `me.saket.telephoto:zoomable-image-coil`

`BUILD.md:702` / `ui/07-EDITOR.md:108` spec a full-screen pager with pinch zoom and predictive-back close. Hand-rolling pinch-zoom that doesn't fight nested scroll, doesn't OOM on a 12 MP photo, and survives rotation is genuinely hard and reliably janky on the first three attempts.

**Telephoto** is a drop-in replacement for async `Image()` with pan/zoom gestures and **automatic sub-sampling of large bitmaps**, so a big image stays sharp fully zoomed without OutOfMemory. It also ships the details you'd otherwise forget: double-tap zoom, single-finger zoom (double-tap-and-hold), **haptic feedback at zoom limits**, nested-scroll compatibility, and state preservation across config change.

That haptic-at-zoom-limit is exactly the class of detail your haptics table is trying to achieve — and it's free.

```kotlin
implementation("me.saket.telephoto:zoomable-image-coil:<current>")
```
Saves ~2 days and is better than what you'd write.

> **DECISION F-29:** ⬜ open — (my rec: yes, clear win)

### F-32 🟢 Konsist — mechanically enforce the rules you keep writing in prose

This one is a philosophical fit rather than a feature. Your corpus is full of laws that currently depend on someone remembering them:

- "Nothing but the wrapper may import `SplitButton`" (F-01)
- "No raw hex in composables — tokens only" (`ui/02-COLOR.md:34`)
- "No hardcoded user-visible English in Kotlin" (`BUILD.md:64`)
- "If you add a haptic not in this table, you are wrong" (`ui/13-HAPTICS.md:29`)
- Domain must not depend on data or UI (`research/14:143`)

**Konsist** is a static analyzer for Kotlin — "ArchUnit for Kotlin" — where architectural rules are written as ordinary JUnit tests, including `assertArchitecture` for layer isolation.

```kotlin
@Test fun `only the expressive wrapper touches alpha Material APIs`() {
    Konsist.scopeFromProject()
        .files
        .filterNot { it.path.contains("ui/common/expressive") }
        .assertFalse { it.text.contains("SplitButton") || it.text.contains("ButtonGroup") }
}
```

Every law in `ui/00-ANTI-JOKE.md` that can be expressed as "this token must not appear here" becomes a failing test instead of a code review someone skips at 11pm. For a spec whose entire premise is *the refusals are the product*, this is the tool that makes the refusals real.

> **DECISION F-32:** ⬜ open — (my rec: yes, ~1 day, and it protects F-01 forever)

## 6. Snappiness playbook

You asked specifically about snappiness. Beyond the baseline profile (F-12), these are the things that actually move perceived speed on a Compose app, in order of effect.

### F-34 🟠 The four that matter most

1. **Baseline profile generated against the real journey** (F-12, and see §1). 30–40% faster startup is the reported effect, and it's the single largest lever. Nothing else on this list is close.
2. **R8 full mode + resource shrinking on release.** Enable `android.enableR8.fullMode=true`. Verify your Convex/Clerk models survive it — serialization + reflection are the usual casualties. Do this *early*; discovering an obfuscation crash at ship time is a bad week.
3. **`LazyColumn`/`LazyVerticalGrid` need both `key` and `contentType`.** `key = { it.id }` is usually remembered; `contentType` almost never is. Without it, Compose can't reuse the right node type between a text card and a thumb card, and your grid scroll pays for it on every fling.
4. **`ProfileInstaller` warm-up + `Modifier.graphicsLayer` for anything animating alpha or translation.** Animating alpha without a graphics layer re-composes; with one, it's a render-thread property change. Your focus-mode chrome fade (`alpha 1 → 0` on the app bar) is exactly this case — do it in a `graphicsLayer` block, not with a recomposing `alpha` parameter.

### F-35 🟡 The perceived-speed trick the spec is missing

There's a category of snappiness that isn't measured in milliseconds: **removing the moments where the app looks like it's thinking.** Your corpus is already excellent at this (no spinners, no skeletons, no toasts). Three more it doesn't cover:

- **Pre-warm the editor's first frame.** On home, when a card enters the viewport, you already have its title and preview. On tap, render the editor's title + first paragraph *from the card's data* immediately, then swap in the full block list when Room returns. First text is on screen in one frame, and `BUILD.md:1199`'s "< 250 ms to first text" becomes "< 16 ms."
- **Never let the IME be the second thing.** `BUILD.md:59` targets keyboard in ≤200 ms. Request focus in the same frame you navigate, not in a `LaunchedEffect` after composition settles — a `LaunchedEffect(Unit)` on the editor runs *after* first composition, which is where the visible delay comes from.
- **Debounce writes, never reads.** Your 50 ms write debounce is right. Make sure no read path is debounced or `distinctUntilChanged`-ed in a way that delays first paint.

### F-36 🟡 Measure the right number

`BUILD.md:1201` says "no bind hitch > 8 ms on 120 Hz." That's a good instinct but not the standard KPI. Use **P95 frame time < 16 ms** as the gate (with P99 tracked but not gating), because a single 20 ms frame during a fling is invisible while a consistently degraded P95 is exactly what "feels laggy" means. Track it in Macrobenchmark, fail CI at +15% startup regression.

## 8. One thing I'd say at the end

Grok's closing line — *a springy plus on a sync model that can drop a note is not premium* — is the most useful sentence produced across all three rounds, and I'd put it in `BUILD.md` above §20.
